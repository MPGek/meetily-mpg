# Design

## Context

See `proposal.md` for motivation and the full dead-reference audit. Additional context that shapes the approach:

- `docs/CODEBASE_MAP*.md` carries a YAML frontmatter (`last_mapped`, `parent`, `section`/`module`) and a banner "Auto-generated by Cartographer" — this was itself generated by some prior tool, not hand-authored from scratch, and has not been regenerated since 2026-08-25 (git-touched 2026-08-31, 18 days stale as of 2026-09-18 and now landing after changes 01-10 which touch most of the modules these files describe: dead code removal, lock hardening, the diarization engine facade, the speaker repository split, recording command split, the frontend typed IPC layer, and this very LLM HTTP client change). Re-running the same kind of tool would immediately be stale again after change 01-10's own edits land, which is the core argument for recommendation B over A.
- `AGENTS.md` lines 5-21 link to all 17 `CODEBASE_MAP*.md` files; line 23 is a single unbroken paragraph enumerating features added since three different dates (2026-08-25, 2026-08-14, 2026-08-05) that has clearly been appended to by hand each time without ever being trimmed — the failure mode recommendation B is designed to stop.
- `graphify-out/` already exists (graph.json, GRAPH_REPORT.md, manifest.json, dated updates from 2026-08-12 through 2026-09-15) and `AGENTS.md`'s own graphify section (lines 33-44) already instructs "If `graphify-out/wiki/index.md` exists, use it for broad navigation instead of raw source browsing" — but that file does not exist yet (`graphify-out/wiki/` has never been generated; the graphify skill's `--wiki` flag "build agent-crawlable wiki (index.md + one article per community)" has not been invoked). AGENTS.md is already written as if the wiki might exist; this change is what actually produces it and removes the hand-written fallback it was meant to replace.
- The specific errors found (fabricated `trait LlmProvider`; `AnalyticsTracker` vs. actual `AnalyticsClient`; a dead link to a plan document that never existed) are not link-rot fixable by a path-existence checker — they are claims about code structure and symbol names that were wrong the day they were written or drifted after a rename, and a hand-maintained doc has no mechanism to catch this short of a human re-reading the source on every edit. `graphify`'s AST-based extraction reads the real symbols on every `graphify update .`, so it cannot independently invent a trait that isn't there.

## Goals / Non-Goals

**Goals:**
- Every remaining backticked file reference in `docs/*.md` and `AGENTS.md` resolves to a real file.
- The kept docs (`CODEBASE_MAP.md`, `CODEBASE_MAP_ARCHITECTURE.md`, `CODEBASE_MAP_CONVENTIONS.md`, `CODEBASE_MAP_OPERATIONS.md`) contain only content stable enough to not need updating every time a module is refactored (system-level architecture, naming conventions, build/run commands) — no per-file token counts, no per-symbol tables, no "recent work" prose.
- `AGENTS.md` stops accumulating a hand-written changelog paragraph and instead points at a source of truth that updates itself as part of the existing OpenSpec workflow (`openspec/changes/archive/`).
- A mechanical doc-link check exists and runs in CI (non-blocking), so future dead references are visible instead of silently accumulating for three more weeks.

**Non-Goals:**
- Running `graphify update . --wiki` to completion and shipping its output is a task in this change (see tasks.md), but designing or modifying `graphify` itself is out of scope — it is an already-installed, already-adopted tool.
- No code changes; `skip_specs: true` is set because nothing here is spec-level application behavior.
- Not attempting to keep the 13 removed files' content anywhere in `docs/` "just in case" — they are superseded by the wiki, not archived alongside it (git history is the archive if anyone needs the old text).
- Not building a symbol-level or semantic doc-accuracy checker (one that would have caught the `AnalyticsTracker`/`AnalyticsClient` or fabricated-trait errors) — that is a much larger undertaking than a path-existence script, and it's precisely the job recommendation B hands to graphify's AST-based regeneration instead of building bespoke tooling for it.

## Decisions

### D1: Recommendation B — thin, stable maps + graphify wiki, not a full manual refresh (A)

Rejected A (refresh all 17 files' content by hand) because:
- The content is not just late — parts are actively fabricated (a `trait LlmProvider` that has never existed) or wrong (`AnalyticsTracker` vs. `AnalyticsClient`), meaning "refresh" would mean re-writing most of the per-module files from scratch by re-reading the source, which is exactly the effort a prior "Cartographer" pass already spent and that decayed in three weeks.
- Changes 01-10 (landing immediately before this change) restructure several of the exact modules these files describe (audio/diarization split into an engine facade, speaker repository split into submodules, recording commands split, a new `llm/` module) — a hand refresh done now would describe the pre-01-10 shape and go stale again within the same PR series.
- The repo has already standardized on `graphify` (`AGENTS.md` lines 33-44) for codebase questions; maintaining a second, parallel, hand-written index is duplicate effort with a worse staleness profile (graphify updates via `graphify update .` after every code change; the hand-written maps update on nobody's schedule).

Chose B: keep only the four files whose content is genuinely stable (system overview, conventions, build/operations commands), delete the 13 file/module-level listing docs, and have `AGENTS.md` send codebase-navigation questions to the graphify wiki instead.

### D2: `scripts/check-doc-links.sh` checks path existence only, not content accuracy

The script is deliberately narrow: extract every backticked string matching `*.rs`, `*.ts`, `*.tsx`, `*.js`, or `*.jsx` from `docs/*.md` and `AGENTS.md`; for each, check whether a file with that basename exists anywhere under `frontend/src-tauri/src/`, `frontend/src/`, `frontend/`, `scripts/`, or the repo root (excluding `node_modules`, `target`, `.git`, `graphify-out`, `.next`, `dist`, `build`); print any that resolve nowhere and exit non-zero if any are found. Markdown-to-markdown links (e.g. the dead `AUDIO_MODULARIZATION_PLAN.md` reference) are out of scope for the automated script in this change — that one is fixed by hand in task 2 — see Open Questions for extending the script later.

- Why basename-anywhere rather than exact relative-path resolution: the kept docs (post-B) mostly name files without full paths (e.g. "``build-gpu.bat``"), and requiring an exact path would force every doc author to spell out full repo-relative paths, which the existing docs never did. This mirrors the audit method used in proposal.md's Impact section.
- Why not check symbol names or prose claims: that requires parsing/understanding code semantics, which is a different (and much larger) tool — exactly the job being handed to graphify instead of built by hand here (see Non-Goals).
- Alternative considered: a Node script under `scripts/` (the repo already has `scripts/*.js`). Rejected in favor of a small POSIX shell script — no new dependency, and CI already runs on `ubuntu-latest` per `pr-main-check.yml`; a shell script also runs identically in a local dev shell without a Node install being relevant to the check. (If implementation finds `grep`/`find`-based shell logic too fragile for the extraction regex, falling back to a small Node script under `scripts/` is an acceptable substitution — the CI wiring and non-blocking behavior are the actual requirement, not the implementation language.)

### D3: Wire the checker into `pr-main-check.yml` as non-blocking

`pr-main-check.yml` currently only runs on `workflow_dispatch` (manual) and does version/branch checks (no test or build steps). Add a new step after "Validate version format":
```yaml
- name: Check documentation links
  run: bash scripts/check-doc-links.sh
  continue-on-error: true
```
- Why non-blocking: this workflow gates release readiness checks today; a doc-link regression should be visible (the step will show as failed-but-non-blocking in the run summary) without blocking a release on documentation, especially while the wiki-based approach is new and the script itself is unproven at catching every real case.
- Why this workflow and not another: `pr-main-check.yml` is the one explicitly named in the assignment and is the natural home for a lightweight repo-hygiene check; the build workflows (`build-windows.yml` etc.) are heavyweight compiled-artifact pipelines where a docs check doesn't belong.

### D4: `AGENTS.md` changelog becomes a pointer, not a paragraph

Replace the "Recent additions" paragraph (line 23) with: "For a changelog of what has shipped, see `openspec/changes/archive/` (each archived change keeps its `proposal.md`; browse newest-first by archive folder name/date) rather than a paragraph maintained here." This removes the only part of `AGENTS.md` that required manual, unbounded editing after every change, while keeping the actual historical record (already produced as a side effect of the existing OpenSpec archive workflow) as the source of truth.

- Alternative considered: keep a short, capped "last 3 changes" paragraph and trim older entries. Rejected: it still requires someone to remember to edit `AGENTS.md` by hand on every change, which is the exact failure mode being fixed; a pointer requires no maintenance.

## Risks / Trade-offs

- **Deleting the 13 module-detail files removes some genuinely useful narrative (diagrams, "why" explanations) that a pure AST-derived wiki article may not reproduce as prose** → Mitigated by graphify's wiki being "agent-crawlable" per-community articles (not just a file list) and by `GRAPH_REPORT.md` remaining available for broader narrative review per `AGENTS.md`'s existing instructions; git history preserves the deleted files' text if anyone needs to recover specific wording.
- **`graphify update . --wiki` has not been run against this exact codebase state before** → Task 5 in tasks.md runs it and verifies `graphify-out/wiki/index.md` exists and is non-empty before `AGENTS.md`'s pointer is finalized; if the wiki generation fails or the output is unusable, the fallback is to keep the current (trimmed) `CODEBASE_MAP.md` set as the sole navigation aid and flag this as a follow-up rather than blocking this change indefinitely.
- **A non-blocking CI check can be ignored indefinitely, reproducing the exact staleness this change fixes** → Accepted for now (matches the assignment's explicit "wire it in as non-blocking"); making it blocking is a natural follow-up once the script has run clean for a while.
- **This change depends on 01-10 landing first**, so file/symbol references written into the four kept docs must reflect the *post*-01-10 codebase (e.g. the new `llm/` module from this same series, the split speaker repository from change 06) — writing them now, before 01-10 lands, risks describing a state that doesn't exist yet → Mitigated by keeping the four surviving docs' content at the system/architecture level (which doesn't name individual post-split file paths) rather than file-level detail, and by tasks.md task 4 explicitly calling out confirming exact command names against the landed implementation of changes 02/03.

## Migration Plan

- Pure documentation/tooling change, additive-then-subtractive: add the new script and CI step first (task order in tasks.md), then trim/delete the docs, so the link checker can validate the *end state* of the docs before archiving this change.
- Rollback: revert the commit(s); deleted files are recoverable from git history, and the CI step is `continue-on-error`, so removing it has no gating impact either way.

## Open Questions

- Should `graphify-out/wiki/` be committed to the repo (so it's available without regenerating), or generated on demand / in CI? Left for the implementer: committing keeps zero-setup navigation working for anyone browsing the repo; generating on demand avoids committing a large derived artifact. Either satisfies this change's goals.
- Should the doc-link checker eventually also crawl markdown-to-markdown links (like the dead `AUDIO_MODULARIZATION_PLAN.md` reference) in addition to code-file references? The current script (D2) only targets code-file extensions; extending the regex to `.md` is a small follow-up, not required to close this change's scope.
