- ✅ *What this change owns — passes.* Persistence came from the existing stop-time split path only: 90 saved rows carry the `_split<N>` suffix produced by stop-time N-way token expansion, and the live module wrote nothing (grep of `live_diarization_reconcile.rs` finds no `SHARED_SEGMENTS`/`sqlx`/INSERT/UPDATE call anywhere). - ❌ *"Per-speaker rows match the live sub-rows' speakers and spans" — fails, for reasons outside this change.* The user reported live labels were visually correct, but after stop most unconfirmed rows collapsed onto one identity. Measured in the DB: cluster `SPEAKER_00` took **382 of 475** System rows (80%), spanning **16.8s → 3044.6s** — the whole meeting, edge to edge, 1981s of audio (~65% of total) — while the other 72 labels hold 1–11 rows each. That timeline spread is the signature of the nearest-turn / gap-fill fallback in `find_best_speaker` acting as a catch-all when transcripts find no overlapping turn, not of a genuinely dominant speaker in a ~10-person call.

**Root-cause evidence gathered for `05b-live-diarization-accuracy`** (added `frontend/src-tauri/tests/replay_stop_time_collapse.rs`, which replays this exact session through `process_chunk` + `finalize`, bypassing every mpsc channel): Fast with the user's `max_speakers=0` produces a *healthy* distribution — top cluster 18.8%, 33 distinct clusters — while Efficient with `max_speakers=10` collapses to **90.8% on one cluster** (4 clusters total). So AHC over-merges badly on this audio, and the production Fast collapse is not reproduced by fixed-0.6s-chunk input. The difference between replay and production is input granularity (replay feeds 0.6s chunks; production feeds VAD-merged segments up to 25s), which points at exactly the `AudioSource` unification 05b scopes; the pre-existing `repro_online_diarization.rs` already carries dedicated 8s and 25s chunk variants, suggesting chunk-size sensitivity was suspected here before.
